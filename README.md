# 핵심 파이프라인 설계 — 예산 기반 여행 계획 에이전트

> **설계 목표**: 단순히 "입력값을 LLM에 던져 요약을 받는" 1회성 API 호출을 넘어서, 서비스 도메인(예산 여행)에 맞게 **검색(Retrieval) · 판별(Classification) · 분기(Branching) · 멀티스텝(Multi-step) · 검증(Validation)** 이 유기적으로 연결된 파이프라인을 설계한다.

---

## 1. 문제 정의 — 왜 단일 호출로는 부족한가

현재 구현(`OpenRouterService.summarizePlan()`)은 입력값을 프롬프트로 만들어 한 번 호출하고 JSON을 받는다. 이 방식의 한계:

- **환각(Hallucination)**: 항공·숙소 실제 시세를 모르는 상태에서 LLM이 예산 배분을 "지어낸다".
- **분기 부재**: 국내/해외, 예산 과부족 등 상황별 처리가 없어 모든 입력을 동일하게 취급.
- **검증 부재**: `amount` 합계가 총예산과 안 맞거나 고정비가 예산을 초과해도 그대로 노출.
- **확장 불가**: 항공/숙소/맛집/서류 화면이 각각 따로 놀고, AI가 이들을 오케스트레이션하지 못함.

→ 그래서 아래처럼 **오케스트레이터가 여러 단계를 조율하는 에이전트 파이프라인**으로 재설계한다.

---

## 2. 전체 파이프라인 개요

```
[온보딩 입력: TripPlan]
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Stage 0. 입력 정규화 & 결측/이상치 판별                        │
│  - 날짜·예산·목적지 유효성 검사, 박/일 계산, 1인 1일 예산 산출   │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Stage 1. 판별 (Classification / Routing)                      │
│  - 국내 vs 해외                                                │
│  - 예산 등급: 알뜰 / 표준 / 여유 (1인 1일 예산 기준)            │
│  - 스타일 → 예산 가중치 프로파일 결정                          │
└─────────────────────────────────────────────────────────────┘
        │
        ├─── 해외 ────► [서류/비자 브랜치] country_doc_rules 조회
        │
        ├─── 예산부족 판별 ►[대안 브랜치] 일정단축·목적지대안·스타일축소 제안
        │
        ▼ (정상 경로)
┌─────────────────────────────────────────────────────────────┐
│ Stage 2. 검색 / RAG (Retrieval, 근거 확보)                     │
│  - 항공권 최저가·숙소 시세·맛집/활동·환율 조회 (툴 호출)         │
│  - 국가별 서류 규칙(내장 지식베이스) 검색                        │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Stage 3. 멀티스텝 예산 추론 (Multi-step, 툴 사용 에이전트)      │
│  A) 고정비(항공+숙소) 실측 계산                                │
│  B) 잔여예산 = 총예산 − 고정비                                 │
│  C) 잔여를 스타일 가중치로 식비/활동/쇼핑/예비 배분             │
│  D) LLM이 검색된 실데이터를 인용해 highlights·팁 생성           │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ Stage 4. 검증 & 자기수정 루프 (Validation / Self-correction)  │
│  - amount 합계 = 총예산? percent 합계 = 100?                   │
│  - 고정비 > 총예산? → Stage 1 대안 브랜치로 회귀                │
│  - 실패 시 재프롬프트 (최대 N회)                               │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
[TripSummary 조립 → 화면 표시 → 확정 시 /trips 저장]
```

## 3. 단계별 상세 설계

### Stage 0 — 입력 정규화 & 판별
- `TripPlan` 의 결측/이상치를 먼저 걸러 LLM 호출 낭비를 막는다.
  - 날짜 미정 → 기간 기반 계산 불가 표시, 목적지 공백 → 재입력 유도, 예산 0 → 차단.
- 파생값 계산: **여행 일수(박/일)**, **1인 1일 예산 = 총예산 ÷ 인원 ÷ 일수**. 이후 모든 판별의 기준이 된다.

### Stage 1 — 판별 (Classification / Routing)
LLM에 넘기기 전에 **규칙 기반 + LLM 판별**을 섞어 경로를 결정한다.

| 판별 항목 | 방법 | 결과가 바꾸는 것 |
|---|---|---|
| 국내 / 해외 | 목적지 문자열 판별(규칙) | 서류 브랜치, 환율 검색, 항공 검색 범위 |
| 예산 등급 | 1인 1일 예산 임계값(규칙) | 숙소 등급, 대안 제안 여부 |
| 스타일 가중치 | 선택 스타일 → 프로파일 매핑 | 카테고리별 배분 비중 (맛집→식비↑, 쇼핑→쇼핑↑) |

> 규칙으로 처리 가능한 판별은 규칙으로(빠르고 결정적), 모호한 판별만 LLM에 맡겨 **비용·지연·환각을 줄인다.**

### Stage 2 — 분기 (Branching)
- **해외 브랜치**: `country_doc_rules.dart` 를 조회해 비자·여권·필수 서류를 체크리스트(`ChecklistStore`)에 자동 반영. 국내면 이 단계 스킵.
- **예산 부족 브랜치**: 고정비 추정이 총예산을 넘을 것으로 판별되면 요약 대신 **대안 3종**(일정 단축 / 근거리 목적지 / 스타일 축소)을 먼저 제안.
- 정상 브랜치만 다음 검색 단계로 진행.

### Stage 3 — 검색 / RAG (Retrieval)
LLM이 예산을 "상상"하지 않도록 **실데이터로 근거를 채운다.** 이미 있는 화면 기능을 툴로 노출:

- `searchFlights(origin, dest, dates)` → 항공 최저가 (Flight 화면 로직 재사용)
- `searchHotels(dest, dates, budgetTier)` → 숙소 시세
- `searchRestaurants/Activities(dest, styles)` → 맛집·활동 후보
- `getExchangeRate(currency)` → 해외 환율
- `getCountryDocRules(country)` → **내장 지식베이스 검색 = 로컬 RAG** (추후 여행 가이드/리뷰 벡터 검색으로 확장 가능)

이 결과를 컨텍스트로 주입 → **grounded generation**.

### Stage 4 — 멀티스텝 예산 추론 (Multi-step Agent)
각 스텝이 앞 스텝 결과에 의존하는 **순차 추론**. Function calling(툴 사용)으로 구현:

1. **고정비 계산** — 검색된 항공+숙소 실측치 합산.
2. **잔여예산 산출** — `총예산 − 고정비`.
3. **가변비 배분** — 잔여를 스타일 가중치에 따라 식비·활동·쇼핑·예비로 분배.
4. **인사이트 생성** — LLM이 위 수치와 검색 데이터를 **인용**해 `highlights`(3~5개)와 절약 팁 작성.

→ "한 번 호출"이 아니라 **계산 → 재검색 → 재계산이 가능한 루프 구조.**

### Stage 5 — 검증 & 자기수정 (Validation)
- 하드 제약: `Σamount == 총예산`, `Σpercent == 100`, `amount ≥ 0`.
- 실패 시 LLM에 오류를 되먹여 **재생성**(최대 N회). 현재 `BudgetAllocation._asInt` 의 정수 보정도 이 검증 계층으로 흡수.
- 고정비 초과가 재확인되면 Stage 1의 대안 브랜치로 **회귀**.

## 4. 현재 코드 → 목표 구조 매핑

| 지금 | 바뀌는 방향 |
|---|---|
| `OpenRouterService.summarizePlan()` 단일 호출 | `TripPlanningPipeline` 오케스트레이터가 Stage 0~5를 조율 |
| LLM이 예산을 추정 | 항공/숙소/환율 **툴 검색 결과를 주입**(grounded) |
| 분기 없음 | 국내/해외·예산과부족 **라우팅 & 브랜치** |
| 검증 없음 | 합계·제약 **검증 + 자기수정 루프** |
| 화면 기능이 독립적 | Flight/Hotel/Restaurant/Docs 로직을 **에이전트 툴로 재사용** |

> 핵심: `TripService.previewPlan()` 이 이미 경계로 분리돼 있어, 그 뒤를 단일 호출 → 파이프라인으로 교체하면 화면 코드 변경 없이 확장 가능하다.

---

## 5. 이 설계가 "단순 API 호출"과 다른 이유 (요약)

- **검색**: 항공·숙소·환율·서류를 실제로 조회해 근거 있는 답을 만든다(RAG).
- **판별**: 국내/해외·예산 등급·스타일을 분류해 경로를 정한다.
- **분기**: 상황별로 서류 브랜치·대안 제안 브랜치로 갈라진다.
- **멀티스텝**: 고정비 → 잔여 → 배분 → 인사이트로 이어지는 순차·툴 사용 추론.
- **검증**: 예산 제약을 강제하고 실패 시 스스로 교정한다.

→ LLM은 파이프라인의 **한 구성요소**일 뿐이고, 서비스 로직(예산 계산·분기·검증)이 전체를 통제한다.
